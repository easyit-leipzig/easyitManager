DataForm 5 – dataformContext

Technische Referenz des standardisierten Übergabeobjekts für DataForm-Aktionen, Recordset-Lifecycle und JavaScript-Callbacks. Das Objekt beschreibt den aktuellen fachlichen und technischen Zustand einer DataForm zu einem eindeutig definierten Zeitpunkt.

1. Ziel und Grundprinzip

dataformContext ist der einheitliche Übergabevertrag zwischen DataForm-Kern, Recordsets, Aktionssystem und benutzerdefinierten JavaScript-Callbacks. Eine Aktion wie Öffnen, Neu, Bearbeiten, Speichern, Löschen oder Navigieren soll nicht mit verstreuten Einzelparametern arbeiten. Stattdessen erhält sie genau ein benanntes Objekt, das den gegenwärtigen Zustand der DataForm als Snapshot beschreibt.

Kernregel: Jeder DataForm-Lifecycle-Callback erhält das Objekt unter dem Namen dataformContext. Für das Recordset-Feld „Nach Speichern“ ist damit beispielsweise afterSave(dataformContext) eine gültige und eindeutig verständliche Konfiguration.

Der Kontext ist bewusst JSON-kompatibel. Er darf keine DOM-Elemente, JavaScript-Funktionen, Datenbankverbindungen oder andere nicht serialisierbare Laufzeitobjekte enthalten. Dadurch kann derselbe Vertrag im Browser, beim Logging, in Tests, über interne APIs und – soweit erforderlich – serverseitig verwendet werden.

Ein ObjektKein wachsender Satz positionsabhängiger Callback-Parameter.
SnapshotDer Zustand gehört exakt zu einem Event und einer Lifecycle-Phase.
SerialisierbarDer Kerninhalt muss mit JSON.stringify() abbildbar sein.
ErweiterbarNeue Felder werden versionskompatibel ergänzt.

2. Lifecycle des Kontextobjekts

Für jede ausgeführte Aktion erzeugt der DataForm-Kern einen neuen Kontext. Ein „before“-Kontext dokumentiert die Situation unmittelbar vor der Operation; ein „after“-Kontext wird nach der Operation neu aufgebaut und enthält zusätzlich das Operationsergebnis. Auf diese Weise kann afterSave(dataformContext) sowohl die tatsächlich gespeicherten Werte als auch den vorherigen Zustand und die während des Speicherns entstandenen Änderungen auswerten.

PhaseBeispielBedeutung
beforebeforeSaveZustand vor der persistierenden Operation. Geeignet für Prüfungen, Abbruch oder Ergänzung kontrollierter Aktionsoptionen.
executesaveInterne Ausführung durch den DataForm-Kern bzw. den Datenadapter.
afterafterSaveNeu aufgebauter Zustand nach erfolgreicher oder fehlgeschlagener Operation; result ist gesetzt.
 
UI-Aktion
   │
   ├── buildContext("save", "before")
   │        └── beforeSave(dataformContext)
   │
   ├── DataForm/Recordset speichert
   │
   └── buildContext("save", "after", result)
            └── afterSave(dataformContext)

4. Standardisierte DataForm-Aktionen

Die Aktionskennung in event.action und event.actionId sollte aus einer zentralen Registry stammen. Dadurch bleibt die fachliche Aktion unabhängig von der visuellen Schaltfläche. Für die bestehenden DataForm-CRUD- und Navigationsfunktionen ist folgende Normierung vorgesehen:

actionbefore-Eventafter-EventZweck
openbeforeOpenafterOpenDatensatz öffnen/anzeigen.
newbeforeNewafterNewNeuen Satz initialisieren.
editbeforeEditafterEditBearbeitungsmodus aktivieren.
savebeforeSaveafterSaveInsert oder Update persistieren.
deletebeforeDeleteafterDeleteDatensatz löschen.
cancelbeforeCancelafterCancelBearbeitung verwerfen/beenden.
refreshbeforeRefreshafterRefreshRecordset/DataForm neu laden.
firstbeforeNavigateafterNavigateZum ersten Datensatz.
previousbeforeNavigateafterNavigateZum vorherigen Datensatz.
nextbeforeNavigateafterNavigateZum nächsten Datensatz.
lastbeforeNavigateafterNavigateZum letzten Datensatz.
Die Button-Grafik oder der lokale Tooltip ist nicht Teil des Kontextvertrags. actionId referenziert die zentrale Aktion; Titel, title, aria-label und PNG-Zuordnung bleiben zentral in der Button-Registry definiert.

5. Recordset-Callbacks

Ein Recordset kann Lifecycle-Felder wie „Vor Speichern“ oder „Nach Speichern“ besitzen. In diesen Feldern wird kein beliebiger JavaScript-Programmtext benötigt. Der empfohlene Vertrag ist ein benannter Callback mit genau einem Kontextargument.

Recordset-FeldBeispielwertAufruf durch DataForm
Vor ÖffnenbeforeOpen(dataformContext)vor dem Öffnen
Nach ÖffnenafterOpen(dataformContext)nach dem Öffnen
Vor SpeichernbeforeSave(dataformContext)vor Insert/Update
Nach SpeichernafterSave(dataformContext)nach bestätigtem Save-Versuch
Vor LöschenbeforeDelete(dataformContext)vor Delete
Nach LöschenafterDelete(dataformContext)nach Delete-Versuch
Keine Verwendung von eval(). Die Callback-Konfiguration soll geparst bzw. gegen eine Callback-Registry aufgelöst werden. Zulässig ist beispielsweise der Funktionsname afterSave oder die deklarative Schreibweise afterSave(dataformContext); der Kern übergibt das Objekt selbst.

5.1 Empfohlene Callback-Registry

DataFormCallbacks.register("afterSave", function (dataformContext) {
    console.log("Gespeichert:", dataformContext.record.id);
});

DataFormCallbacks.invoke("afterSave", dataformContext);

5.2 Zulässige Rückgabe für before-Callbacks

Ein before*-Callback kann die Aktion zulassen oder kontrolliert abbrechen. Damit bleibt das Verhalten testbar und frei von versteckten Seiteneffekten.

// Aktion zulassen:
return true;

// Aktion abbrechen:
return false;

// Alternativ normiertes Ergebnis:
return {
    cancel: true,
    message: "Der Datensatz darf in diesem Zustand nicht gespeichert werden."
};

Bei after*-Callbacks dient der Kontext primär zur Reaktion auf das abgeschlossene Ergebnis. Der Persistenzstatus selbst darf nicht nachträglich durch einen Rückgabewert des Callbacks umgedeutet werden.

6. afterSave(dataformContext) – Referenz

Das Recordset-Feld „Nach Speichern“ kann den Wert afterSave(dataformContext) tragen. DataForm ruft diese Methode auf, nachdem der Speichervorgang ein Ergebnis geliefert und der Kontext neu synchronisiert wurde.

function afterSave(dataformContext) {
    if (!dataformContext.result?.success) {
        console.error(
            "Speichern fehlgeschlagen:",
            dataformContext.result?.error?.message
        );
        return;
    }

    console.log("Recordset:", dataformContext.recordset.name);
    console.log("ID:", dataformContext.record.id);
    console.log("Aktuelle Werte:", dataformContext.values.current);
    console.log("Änderungen:", dataformContext.values.changed);
}

6.1 Insert erkennen

function afterSave(dataformContext) {
    const wasInsert =
        dataformContext.result.success &&
        dataformContext.result.operation === "insert";

    if (wasInsert) {
        console.log(
            "Neuer Datensatz mit ID",
            dataformContext.result.recordId
        );
    }
}

6.2 Update und einzelne Feldänderungen erkennen

function afterSave(dataformContext) {
    if (!dataformContext.result.success) return;

    const nameChange = dataformContext.values.changed.name;

    if (nameChange) {
        console.log("Alt:", nameChange.oldValue);
        console.log("Neu:", nameChange.newValue);
    }
}

6.3 Eltern-/Kindbezug auswerten

function afterSave(dataformContext) {
    const parent = dataformContext.relations.parent;

    if (parent) {
        console.log(
            "Kind gespeichert für",
            parent.recordsetName,
            parent.keyField,
            parent.keyValue
        );
    }
}

8. Verbindliche Regeln des Vertrags

  1. Ein Parameter: Custom-Callbacks erhalten genau das benannte Objekt dataformContext.
  2. JSON-kompatibel: Keine Funktionen, DOM-Knoten, zyklischen Referenzen oder Connection-Objekte im serialisierbaren Kontext.
  3. Snapshot statt Live-Objekt: Der Kontext beschreibt den Zustand zum Eventzeitpunkt. Ein späterer UI-Zustand darf einen bereits erzeugten Kontext nicht stillschweigend verändern.
  4. Original und Current getrennt: values.original und values.current dürfen nicht auf dieselbe veränderbare Objektinstanz zeigen.
  5. Nach Save neu synchronisieren: Bei afterSave müssen serverseitig erzeugte Schlüssel bzw. normalisierte Werte in record und values.current enthalten sein.
  6. Result nur als Ergebnis: result.success spiegelt die reale Persistenzoperation wider und darf nicht allein aus dem Rückgabewert eines UI-Callbacks abgeleitet werden.
  7. Keine Geheimnisse: Passwörter, Tokens, Connection-Strings und interne Stacktraces gehören nicht in den Client-Kontext.
  8. Registry statt eval: Callback-Namen werden gegen eine definierte Registry bzw. sichere Namensauflösung ausgeführt.
  9. Abwärtskompatibilität: Erweiterungen innerhalb derselben Major-Version dürfen bestehende Felder nicht umdeuten.
  10. Aktion ≠ Button: Der Kontext transportiert die fachliche Aktions-ID. PNG, Titel und ARIA-Beschriftung bleiben Verantwortung der zentralen Button-Registry.

10.2 Änderungen bestimmen

function diffValues(original, current) {
    const result = {};
    const keys = new Set([
        ...Object.keys(original ?? {}),
        ...Object.keys(current ?? {})
    ]);

    for (const key of keys) {
        const oldValue = original?.[key] ?? null;
        const newValue = current?.[key] ?? null;

        if (!Object.is(oldValue, newValue)) {
            result[key] = { oldValue, newValue };
        }
    }

    return result;
}

10.3 Sichere Callback-Auflösung

const DataFormCallbacks = (() => {
    const callbacks = new Map();

    return {
        register(name, fn) {
            if (!/^[A-Za-z_$][A-Za-z0-9_$]*$/.test(name)) {
                throw new Error("Ungültiger Callback-Name.");
            }
            if (typeof fn !== "function") {
                throw new TypeError("Callback muss eine Funktion sein.");
            }
            callbacks.set(name, fn);
        },

        invoke(configValue, dataformContext) {
            if (!configValue) return undefined;

            const match = String(configValue).trim().match(
                /^([A-Za-z_$][A-Za-z0-9_$]*)(?:\(\s*dataformContext\s*\))?$/
            );

            if (!match) {
                throw new Error(
                    "Ungültige Callback-Konfiguration: " + configValue
                );
            }

            const fn = callbacks.get(match[1]);
            if (!fn) {
                throw new Error(
                    "Callback nicht registriert: " + match[1]
                );
            }

            return fn(dataformContext);
        }
    };
})();

10.4 Save-Lifecycle

async function saveRecord(recordsetRuntime) {
    const beforeContext = buildContextForRecordset(
        recordsetRuntime,
        "beforeSave",
        "save",
        "before"
    );

    const beforeResult = DataFormCallbacks.invoke(
        recordsetRuntime.callbacks.beforeSave,
        beforeContext
    );

    if (
        beforeResult === false ||
        beforeResult?.cancel === true
    ) {
        return {
            success: false,
            status: "cancelled",
            message: beforeResult?.message ?? null
        };
    }

    const saveResult = await recordsetRuntime.persist();

    // Wichtig: Recordset nach der Persistenz synchronisieren.
    await recordsetRuntime.syncAfterSave(saveResult);

    const afterContext = buildContextForRecordset(
        recordsetRuntime,
        "afterSave",
        "save",
        "after",
        saveResult
    );

    DataFormCallbacks.invoke(
        recordsetRuntime.callbacks.afterSave,
        afterContext
    );

    return saveResult;
}

12. Versionierung und Erweiterbarkeit

Der Vertrag verwendet semantische Versionierung. Neue optionale Felder dürfen in einer Minor-Version ergänzt werden. Das Entfernen, Umbenennen oder Bedeutungsändern bestehender Felder erfordert eine neue Major-Version. Ein Callback sollte unbekannte zusätzliche Felder deshalb tolerieren und ausschließlich auf die Felder zugreifen, die er tatsächlich benötigt.

ÄnderungBeispielVersion
Optionales Feld hinzufügenui.timezone1.1.0
Neue Action ergänzenduplicate1.1.0, sofern bestehende Semantik unverändert bleibt
Feld umbenennenrecord.id → anderer Name2.0.0
Semantik änderncurrentIndex von 0- auf 1-basiert2.0.0
Empfohlener Integrationspunkt: dataformContext sollte im DataForm-5-Kern zentral erzeugt werden. Weder einzelne Seiten noch CRUD-Buttons noch Recordsets sollten eigene, abweichende Kontextvarianten konstruieren.

13.23 Zentrale Callback-Registry

const DataFormCallbacks = (() => {
    const registry = new Map();

    function register(name, callback) {
        if (typeof callback !== "function") {
            throw new TypeError(
                "Callback muss eine Funktion sein."
            );
        }

        registry.set(name, callback);
    }

    function invoke(
        callbackDefinition,
        dataformContext
    ) {
        if (!callbackDefinition) return;

        const match =
            String(callbackDefinition)
                .trim()
                .match(
                    /^([A-Za-z_$][A-Za-z0-9_$]*)(?:\(\s*dataformContext\s*\))?$/
                );

        if (!match) {
            throw new Error(
                "Ungültige Callback-Konfiguration."
            );
        }

        const callback =
            registry.get(match[1]);

        if (!callback) {
            throw new Error(
                "Callback nicht registriert: " +
                match[1]
            );
        }

        return callback(dataformContext);
    }

    return {
        register,
        invoke
    };
})();

13.26 Vollständiger Save-Lifecycle

async function executeSave(recordsetRuntime) {

    // Kontext vor Save
    const beforeContext =
        buildContextForRecordset(
            recordsetRuntime,
            "beforeSave",
            "save",
            "before"
        );

    // beforeSave
    const beforeResult =
        DataFormCallbacks.invoke(
            recordsetRuntime.callbacks.beforeSave,
            beforeContext
        );

    // Abbruch
    if (
        beforeResult === false ||
        beforeResult?.cancel === true
    ) {
        return {
            success: false,
            status: "cancelled",
            message:
                beforeResult?.message
                ?? "Speichern abgebrochen."
        };
    }

    // Persistenz
    const saveResult =
        await recordsetRuntime.persist();

    // neuen DB-Zustand übernehmen
    await recordsetRuntime.syncAfterSave(
        saveResult
    );

    // Kontext nach Save
    const afterContext =
        buildContextForRecordset(
            recordsetRuntime,
            "afterSave",
            "save",
            "after",
            saveResult
        );

    // afterSave
    DataFormCallbacks.invoke(
        recordsetRuntime.callbacks.afterSave,
        afterContext
    );

    return saveResult;
}
